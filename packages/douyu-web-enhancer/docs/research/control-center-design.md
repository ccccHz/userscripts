## 结论

下一项合理的平台能力是**斗鱼页内统一控制中心**：一个可关闭的设置抽屉/面板，运行在
`https://www.douyu.com/*` 当前页面内。它不是外站、独立新标签页，也不应成为把所有功能塞进一个
浮动功能栏的理由。

控制中心与近场入口分工如下：

| 使用频率与对象 | 入口 |
| --- | --- |
| 正在看见的播放器或弹幕区，需要立即改变结果 | 保留在对象附近的近场开关 |
| 跨区域偏好、功能总览、自动化参数、运行结果、日志、备份恢复 | 统一控制中心 |
| 页面入口失效时的诊断/低频兜底 | Tampermonkey GM 菜单 |

因此，现有“前缀”“拉高”仍位于弹幕工具栏，礼物栏仍保留播放器菜单和悬浮快捷开关；控制中心对它们
提供总览和同一规范设置的低频编辑，但不能取消这些就近入口。这个边界既符合现行架构，也符合
[`DWE001`](../decisions.md) 的高频入口迁移约束。

## 原版与当前事实

归档的 `extension-entry-shell` 包含 `ExIcon/`、`ExPanel/`、播放器工具栏菜单，承载精灵球、工具条、
右侧面板和播放器菜单；例如每日签到使用 ExPanel 图标，播放器礼物栏使用菜单与悬浮开关双入口。
详见 [归档全量索引](../migration/archive-inventory.md)。这说明“集中入口壳”是原版的产品事实，但不说明
应将每个高频操作迁入同一个面板。

当前实现已经有三种不同层次的入口：

- 页面近场：弹幕工具栏两个开关，以及播放器菜单/悬浮礼物栏开关；它们会随斗鱼局部重建重新挂载。
- GM 菜单：仅复制诊断信息与自动化日志。
- 隐式全局状态：功能设置、网页全屏偏好、每日自动化账本和审计日志。

每日自动化的路线图已将“集中管理全包功能开关、默认值、自动化参数、执行状态和日志入口”的统一配置页
列为近期前置任务，并明确原页面高频入口继续保留、GM 菜单只作配置页完成前的临时兜底。

原版壳的精确视觉、触发器位置、关闭/悬停细节尚未形成完整基准卡。新控制中心可以落实已确认的统一配置
目标，但不得未经对照就宣称其精灵球、位置或动画与原版等价。

## 信息架构（首版）

1. **概览**：本房间正在运行的能力、异常/等待项、版本与“此功能也可从何处近场操作”的说明。
2. **播放与页面**：播放器礼物栏、网页全屏偏好，以及未来低风险播放控制；全屏偏好与本房间运行状态
   分开展示。
3. **弹幕**：历史、发送观察、前缀、布局等；明确提示“前缀/拉高”仍可从弹幕工具栏一键切换。
4. **每日自动化**：总开关、原子任务上次结果/重试资格、有限调度状态、自动荧光棒参数、审计日志入口。
5. **数据与诊断**：复制当前诊断、导出设置、导出脱敏审计、导入、清空审计与恢复默认。

不把“运行任务”“清空数据”“导入覆盖”放进普通功能开关列表，也不以一个笼统的“今日完成”掩盖部分
失败或待重试的自动化子任务。

## 数据与状态分层

控制中心只能展示和修改已有状态所有者，不能成为第二套运行状态。建议后续升级为以下读写边界：

```text
可编辑 SettingsVNext      → 功能开关、全局偏好、明确的自动化参数
只读 RuntimeSnapshot      → runtime + Diagnostics 的当前状态、命中选择器、更新时间
只读 AutomationTaskState  → 每任务最后尝试/成功/结果摘要、锁和重试资格
有界 AuditLog             → 脱敏的 start/finish/skip/error 事件
```

- `SettingsVNext` 是唯一可导入的常规设置。**本段“v5 向后迁移、未知字段丢弃”是 2026-09-15 的研究假设，已由 2026-09-17 的 D034 取代：外部导入必须是完整 v6，未知/缺失字段明确拒绝；仅既有本地存储可走历史兼容归一化。**
- 当前网页全屏偏好使用独立 GM 键且缺失默认 true；迁移时必须单向兼容到新的规范设置，不能长期双写。
- 每日任务账本、跨 tab 锁、当前页 scheduler 和审计日志属于运行证据，不能被普通设置导入覆盖。
- 面板状态应来自 `SettingsStore`、`FeatureRuntime` 与 `Diagnostics` 的订阅式读模型；不要为刷新状态建立轮询。
  `Diagnostics` 可扩展为变更订阅，页面 UI 仅由此触发重绘。
- 面板切换复用现有“运行时切换、持久化失败则回滚”的事务语义；期望开关与实际状态须同时显示，例如
  “已开启·等待页面元素”或“已开启·降级”，不能只用开关颜色假装功能可用。

## 导入、导出与危险动作

### 导入导出

- **导出设置（默认）**：schema、功能偏好及明确允许的自动化参数；不含 Cookie、token、用户标识、
  聊天正文、锁、任务账本或完整接口响应。
- **诊断/审计导出（单独选择）**：诊断为一次性快照；审计继续沿用现有脱敏、数量和时间上限。
- **导入流程（2026-09-17 D034 已取代早期设想）**：读取 JSON → 完整 v6 schema/白名单/类型校验 → 显示变更差异与每日自动化风险 → 用户确认 → 一次保存 →
  统一 reconcile runtime。校验或保存失败时不改变设置。
- **已取代的旧表述：**“导入设置不触发立即运行自动化”。实际保留既有 feature 语义：若经确认的完整快照将 `dailyAutomation` 从关闭改为开启，runtime 会按“启用即检查”运行，因而确认卡必须提示可能的账号动作。导入仍绝不导入“今日已完成”、锁、重试冷却、审计或发送观察数据。

### 风险分层

| 操作 | 首版交互 |
| --- | --- |
| 纯本地布局/阅读开关 | 直接切换；保存失败回滚并反馈 |
| 暂停已启用自动化 | 可直接暂停，不产生外部账号动作 |
| 启用自动化、立即运行 | 独立确认卡，列出将执行的原子任务、账号影响和失败行为 |
| 导入覆盖、清空审计、恢复默认 | 明确影响范围的确认对话框；不提供“清空全部数据”快捷动作 |

当前 `dailyAutomation` feature 启用时会启动并立即执行 runner；控制中心实现前必须确认是否保持这个语义，
还是改为“启用调度”与“现在运行”分离。后者更清晰，但属于体验与账号授权行为变更，不能暗中调整。

## 宿主、全屏、重建与可访问性

首版建议维护一个可销毁、可重建的 `ControlCenterHost`，由独立 controller 将 DOM 事件转换为受控命令。
近场按钮依旧由各自功能管理，不能让控制中心接管它们的 disposer。

- **宿主（暂定）**：`document.body` 下唯一的 panel root，使用单个 `open` ShadowRoot 隔离样式；面板本身
  不嵌入可能被斗鱼替换的播放器/工具栏节点。
- **尚未冻结的选择**：`open` ShadowRoot 与前缀化 light DOM 都可行。ShadowRoot 可降低斗鱼 CSS 冲突，
  但全屏重挂、字体、定位、可访问性及调试兼容需原型 E2E 验证；若出现兼容缺陷，回退为前缀化 light DOM
  加单个 `StyleRegistry` 样式条目。实现前不得把任一方案写成不可变架构。
- **动态重建**：触发器可借现有共享 `ObserverHub` 幂等补挂；控制中心不建永久轮询，也不监听自己写入而
  自激。关闭、pagehide 或 feature destroy 时必须移除 root、监听器、定时器和样式。
- **全屏**：`fullscreenchange` 时将宿主移动到 `document.fullscreenElement`，退出时恢复 body，确保网页/浏览器
  全屏仍能读取设置且不被裁切。
- **键盘与读屏**：真实 `button`/`label`/`fieldset`；抽屉使用 `role="dialog"`、`aria-modal`、可见标题；
  打开时焦点进入面板，Tab 限制在面板内，Escape 关闭并归还到触发器；状态更新用克制的 `aria-live`，
  不能只靠颜色或 hover。
- **窄屏**：宽屏右侧抽屉（约 360–420px），小于约 640px 改底部全高 sheet，分组可折叠、操作区固定；
  不遮住弹幕输入框，不以 hover 作为唯一入口。

## UI 技术取舍

首版使用原生 DOM + TypeScript DOM factory/受控渲染，不引入 UI 库、UI CDN、运行时模块下载或复杂安装体系。
理由是本包为小型单 userscript、`document-start` 启动且受斗鱼 DOM/全屏生命周期约束；目前 workspace 也没有
前端框架或浏览器 E2E 依赖。额外框架会扩大 bundle、样式隔离和清理验证面，却不能替代体验契约。

若控制中心以后发展为多页复杂表单、虚拟化长日志或大量可组合组件，**Lit** 是首个重新评估的升级候选：
它适合 Web Components/Shadow DOM、可随构建产物本地打包，且比完整 SPA 框架更贴近此宿主模型。引入条件是
首版原生实现已证明维护成本或复杂度失控；不得为“看起来现代”提前加入，也不得从 CDN 加载。

## MVP 与明确非目标

MVP：一个可访问、可关闭的页内控制中心；功能总览与低频开关；每日自动化每任务状态与脱敏日志复制；
诊断复制；设置 JSON 导入/导出；设置迁移与运行时回滚；普通/网页全屏/浏览器全屏/局部重建验证。

明确非目标：复刻所有原版 ExPanel 小工具或视觉；取消现有近场入口；新增账号自动化范围；自动运行导入内容；
全量聊天/发送记录浏览器数据库管理；远程 UI、在线账户、CDN、发布或 metadata 权限扩大。

## 2026-09-17 已实施的数据管理边界（0.10.6）

本实现将上文的研究建议收敛为明确、安全的 Settings v6 契约：导入文件必须含完整的
`schemaVersion`、`features`、`preferences` 与 `automation` 白名单。所有字段精确匹配、类型正确才进入差异预览；
未知或缺失字段、非法房间号与旧 schema 均显示具体原因并拒绝写入，而不是丢弃后猜测用户意图。现有持久化
设置的兼容归一化仍只用于脚本自身历史数据迁移，不使外部导入取得宽松透传入口。

确认导入或恢复默认时，控制中心先列出每个变更，随后将完整快照一次写入 `SettingsStore`；写入成功后才
reconcile `FeatureRuntime`。因此保存失败不会改变内存配置或运行态，失败后的候选和差异仍可供用户取消或重试。
若差异会从关闭改为开启 `dailyAutomation`，确认卡会明确提示该 feature 现有的“启用即检查”账号影响；
本轮没有改变这一业务语义。新安装默认关闭每日自动化，已经保存的用户选择照常保留。

“清空”只对 `AutomationAuditLog` 提供二次确认，不提供清空全部数据。审计下载沿用已有脱敏读取结果；
Settings 导入/导出、恢复默认和审计清空均不触及 Cookie、身份、任务账本、跨标签锁、冷却、聊天内容或其他
runtime 数据。多个标签页在页面重新可见或重新聚焦时从唯一 `SettingsStore` 读取并重新 reconcile，避免另建
轮询或第二状态源。
