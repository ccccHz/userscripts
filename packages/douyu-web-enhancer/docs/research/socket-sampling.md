# 无登录态斗鱼 Socket 采样

状态：研究工具已实现；登录态采样和功能改写均未开始。

## 目的与来源

先用独立 CLI 连接一个房间的 `danmuproxy.douyu.com` 公共弹幕流，记录自然收到的消息，按类型和字段结构分析。此工具不使用页面 Cookie、Token 或 UID，也不改 `douyu-web-enhancer` 的安装包。页面已安装的被动 Hook 保留为后续有争议时的定向对照。

同级历史项目 `Douyu-node` 区分登录态 `wsproxy` 和公共消息 `danmuproxy`，但其默认入口允许终端输入发送弹幕/礼物且保存 Cookie，因此仅参考协议，不运行原入口。当前公共流是否足以覆盖礼物、榜单、背景等需求，必须由自然样本决定。

## 持久化选择

采用**逐帧 JSONL**，每行一个带时间戳的记录；入站帧以 base64 原样保存，供协议解析器以后重新分析。另提供 `analyze` 命令实时重算消息类型、包类型、字段名和值形状（空、数字、URL、文本、嵌套/转义）。不引入数据库依赖：当前只有单进程顺序写入、最多 10 分钟、32 MiB、20,000 帧；按类型索引可由原始数据重新生成。若将来需要长时间、多房间或复杂查询，再评估 SQLite。

文件默认位于 `packages/douyu-web-enhancer/.local/socket-samples/`，该目录被 Git 忽略；新目录权限为 `0700`，新文件为 `0600`。**原始帧可能包含聊天正文、用户标识和其他个人数据**，不要提交、分享或粘贴原文件；CLI 标准输出只有聚合摘要。数据不会自动删除或上传，后续清理须按仓库规则取得用户确认。

## 运行边界

- 只连接指定的一个数字房间，连接建立前最多轮换四个端口，同一时刻至多一条连接；连接成功后断开即停止，不自动无限重连。
- 仅发送公共流连接必需的 `loginreq`、`joingroup` 和 40 秒一次的 `mrkl`。没有聊天、送礼或其他账号命令，也不扫码登录。
- 默认 120 秒，最大 600 秒；单帧上限 1 MiB，总入站数据上限 32 MiB、帧数上限 20,000。到上限、用户 Ctrl-C、断线或超时即关闭连接。
- 不与同房间登录态 CLI 连接并行。用户报告同账号同房间新连接可能顶掉旧连接；登录态测试进入单独阶段前沿用这一操作约束。

## 命令

从仓库根目录运行：

```sh
node packages/douyu-web-enhancer/tools/socket-sampler.mjs capture --room 1126960 --seconds 120
node packages/douyu-web-enhancer/tools/socket-sampler.mjs analyze packages/douyu-web-enhancer/.local/socket-samples/<文件名>.jsonl
```

第一条命令结束时会打印本地文件路径与聚合摘要。第二条可在调整分析器后对同一份样本重新分析；`analyze` 不打开网络连接。

## 后续判断

1. 先分类消息类型及字段，识别礼物、榜单、进场、普通弹幕和无法解析的帧；未自然出现的类型标为缺样本。
2. 对用户屏蔽和关注，检查是否有稳定 UID 与房间标识；对链接、活动图标和装饰，检查字段能否识别对应弹幕。
3. 对背景、head、tail、头像，公共流字段只能证明“数据里有什么”；要判断最终渲染与极简模式无误伤，仍需选取自然消息与页面 DOM 定向配对。
4. 仅当公共流字段不足、发生难解释的 bug 或要全面评估页面控制消息时，再设计登录态采样。届时另行确认扫码或其他凭据方式，不复用或提交本工具的原始文件。

| 房间 | 时长 | 帧 / 消息 | 已见主要类型 | 解释边界 |

| `52` | 90 秒 | 155 / 226 | `chatmsg` 55、`uenter` 47、`dgb` 32、`ranklist` 17、`comm_chatmsg` 20 | 覆盖本房间礼物和三类榜单结构，尚未与页面具体展示配对。 |
| `60937` | 90 秒 | 3 / 4 | `chatmsg` 1、`uenter` 1 | 连接成功但该时段流量很低；不推断长期热度。 |
| `182102` | 60 秒 | 381 / 801 | `chatmsg` 547、`uenter` 211、`dgb` 15 | 根据用户提供的在看排行截图选取，作为高弹幕量对照；0 个未解析帧。 |

`52` 的 `chatmsg`、`uenter`、`dgb` 样本都有 `rid` 与 `uid` 字段；`ranklist` 有 `list_day`、`list`、`list_all`，嵌套条目包含 `uid`、`nickname` 和 `gold` 等字段。因而当前房间的指定用户识别、进场/发言观察和榜单分析具备协议基础；全平台追踪仍需要另外的多房间范围决策。`comm_chatmsg` 内还有嵌套 `chatmsg`，不能简单假设所有文字消息只走顶层 `chatmsg`。

原分析器把一个跨两次 WebSocket 消息送达的协议包误报为两条坏帧。原始帧无损保存后，改用连续流解包重算：`52` 样本从 225 条、2 个未解析帧修正为 226 条、0 个未解析帧。这说明后续判断应基于可重放原始帧的分析结果，不用单帧解析结果推断协议损坏。

普通 `chatmsg` 还有 `ic`、`ail`、`nail`、`lk` 等字段，但名称本身不能证明头像、背景、尾巴、活动图标的实际用途。此类判断需自然消息与页面 DOM 定向配对。`dgb` 包含 `gfid`、`gfcnt` 等礼物字段，仍需对照礼物区、横幅和飘屏。`configscreen`、`rtss_update` 等类型已出现，但不能仅凭同现推断它们控制广告或浏览器行为。

后续长时采样的选房方法：优先尊重用户指定的 `60937`；若当时自然流量不足，可按 [在看直播排行](https://www.doseeing.com/) 的近期 5 分钟/1 小时弹幕榜挑高弹幕房间，按礼物榜挑自然礼物较多的房间。排行是动态参考，记录采样时选房依据；只对实际选择的数字房间建立连接，不批量遍历榜单。

## 下一步需求判定

| 需求 | 当前公共流证据 | 下一验证动作 |
| --- | --- | --- |
| 指定用户屏蔽、关注发言与进场 | `chatmsg`、`uenter` 在自然样本中有 `uid` 与 `rid` | 先定义当前房间与全局规则的优先级；如覆盖飘屏、特殊弹幕，需识别 `comm_chatmsg` 等其他文本类型及页面对应关系。 |
| 弹幕速度 | 高流量样本的 `chatmsg` 可直接计数 | 明确是否计入 `comm_chatmsg`、系统弹幕；处理断线、空闲和换房。 |
| 本房间礼物、日/周/总榜 | `dgb` 有 `gfid`、`gfcnt` 等字段；`ranklist` 有 `list_day`、`list`、`list_all`，其嵌套条目有 `uid`、`gold` | 核对礼物展示区域和榜单实际值；`spbc` 是跨房间广播，不能并作本房间礼物。 |
| 小尾巴、前后缀 | 入站公共流无法证明当前网页的发送链路 | 单独确认用户可见发送语义和授权，再研究页面发送位置；不从入站采样直接开发。 |
| 尾部链接、头部活动图标 | `chatmsg` 有正文及若干扩展字段，尚未建立字段语义 | 对自然命中样本配对消息字段与右栏/飘屏 DOM，确定可识别边界。 |
| 特殊背景、head、tail、头像、极简模式 | 公共流可提供候选字段，未证明最终渲染方式 | 延续已确认的多类型 DOM 采样；若 Socket 字段只能标识类别，采用 Socket 辅助判断与窄范围 DOM/CSS 清理。 |
| 广告、其他页面信号 | 见到 `configscreen`、`rtss_update` 等类型 | 仅在有明确页面事件时做时间配对和因果检查，不按类型名称猜测。 |
