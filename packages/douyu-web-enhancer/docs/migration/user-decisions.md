# 完整迁移用户决策清单

最后更新：2026-09-11

只询问无法从源码或文档得到的偏好与授权。已确认的产品方向在这里形成长期记录；未决定项可以采用
推荐默认值继续低风险路线。任何账号写入、自动执行、权限扩大或外部数据披露仍必须在具体任务中再次确认。

## 已确认的路线图选择

### D0：当前阶段派发任务模型策略

- **状态**：已更新确认（2026-09-19），替换 2026-09-11 的 Terra high 实验策略。
- **用户决定**：调度中心保持当前模型与推理配置；独立执行任务默认显式使用
  `gpt-5.6-luna`、`high` 推理，用户为具体任务另行指定时覆盖默认值。
- **边界**：此决定只规定派发任务 chat，不改变调度中心本身。不得继续向派发任务指定 Sol medium，
  或在没有用户指定时按任务表面复杂度自动更换模型/推理组合。
- **后续执行**：创建、继续和委派迁移任务时均遵循 [DouyuEx 任务分流规则](../task-routing.md)。
  只有用户以后再次明确调整时才能改变；调度器不得自行解除或恢复模型分级。

### D1：保留范围采用“安全价值优先”还是“旧版全部逐项复刻”

- **状态**：已确认（2026-09-04）。
- **用户决定**：采用“全量登记、安全价值优先”；用户会配合按归档功能逐项评估、筛选和排序。
- **推荐答案**：安全价值优先。全量登记，但优先保留简洁模式、纯本地播放/弹幕工具和只读信息；
  账号切换、自动发言/禁言/送礼、旧活动、旧外站默认 `deferred/rejected`。
- **影响**：决定 M1–M5 能否直接排期，也决定“完整”的统计口径。
- **后续执行**：本项不再阻塞；归档登记不等于保留，排期以逐项筛选结果为准。

### D2：新功能前是否先完成简洁模式全屏/动态重建验收

- **状态**：已确认（2026-09-04）。
- **用户决定**：先执行一次简洁模式 M0 完整验收，并把它作为验收工作流试跑。
- **推荐答案**：是；把 M0 作为硬里程碑，但不让缺少自然样本的 SC/特殊限制阻塞 M1。
- **影响**：除固化当前良好体验，还要记录耗时、重复步骤、失败点、可自动化项和可合并证据，产出一份
  工作流复盘，再调整后续功能的验收模板。
- **后续执行**：本项不再阻塞；M0 结果和流程复盘完成后再进入常规迁移批次。

## 已确定暂不提前裁剪的事项

### D3：每日自动化组合如何评估

- **状态**：体验范围已确认（2026-09-13）；各真实账号动作仍须在实机执行前逐项说明目标并取得授权。
- **用户理解**：原版签到是“每日自动化任务”体验组合，覆盖多个原版子任务；独立 package
  `auto-fans-continue` 的自动送荧光棒在产品认知上也属于这个目标，只是自动化程度更高，而归档
  `fans-badge-renewal` 的自动化程度较低。
- **第一批保留范围**：鱼吧签到（不含补签）、客户端签到、粉丝家园、固定帖子阅读、
  固定房间关注任务、等级奖励领取和自动荧光棒。超级粉丝旧接口与 `sign-room` 已分别实测下线，
  不再调用；带日期/活动 alias 的签到进入延伸验证 TODO，不因原版仍调用就宣称当前有效。
- **固定目标策略**：继续使用归档作者选择的固定帖子和固定直播间，避免动态目标影响正常使用；
  只在对应任务未完成时执行，并在关注动作前读取原状态、结束后恢复原状态。
- **自动荧光棒基准**：完整保留现有 `packages/auto-fans-continue` 的实现、默认行为、配置、锁、日志、
  toast 和测试，不采用 DouyuEx 归档的自动/手动续牌实现；后续并入 `douyu-web-enhancer` 的统一代码、
  设置、调度和发布生命周期。
- **共享基础设施**：每日任务共享自动化调度、按任务锁、运行账本、有界审计日志和 toast 服务；
  每个任务仍独立判断完成、失败和可重试状态，不能由一个全局“今日完成”掩盖部分失败。
- **配置入口**：近期优先建设统一配置页，集中管理功能开关、默认行为、自动化配置和日志入口；
  自动荧光棒现有 GM 房间配置只作为配置页完成前的临时入口。
- **首轮实机裁决（2026-09-13）**：超级粉丝归档接口返回 HTTP 404，且当前官方超级粉丝/钻石粉丝
  页面模块未发现替代签到动作，因此不再每天调用旧接口；这是实测后的失效裁剪，不等于裁剪整个
  每日自动化体验。其余失败项先修复运行环境或生命周期问题后跨日复验。
- **直播间签到裁决（2026-09-19）**：用户授权对房间 `5135383` 单次调用归档 Android checkIn 接口，
  传输成功但业务返回 `error: 8 / 功能已下线`；因此 `sign-room` 明确放弃，不再作为待验证原子项。

## 可采用推荐默认值的选择

### D4：归档中已明确失效、未注册或仅导向旧外站的功能

- **推荐答案**：默认放弃，包括电视/广告/点赞签到、AdVideo、MiniProgram、SyncJoy、旧更新检查、
  每周 star 提醒、AutoAnchorStar/fkbuff/在线助手外站入口。
- **影响**：只保留审计记录，不进入 `features.json` 和实现队列。
- **为什么现在可默认**：源码已给出失效/未注册事实，且外站价值和安全边界无法由本项目保证。

### D5：相机截图/GIF 的目标

- **推荐答案**：不迁移 `camera-capture`，而不是复刻“关闭 7 天”；若未来需要截图再作为独立功能重开。
- **影响**：不会加载 gif.js，也不会在播放器增加相机按钮。
- **为什么现在可默认**：现有 TODO 已记录“关闭原版截屏功能”的方向；这里只需确认是永久排除还是保留永久隐藏设置。

### D6：官方已有近似能力时的处理

- **推荐答案**：官方能力能满足同一用户结果时登记 `rejected`；只有明确差异价值才做窄增强。
- **影响**：可能放弃影院、字号、原生画中画等重复能力，减少 DOM 摩擦。
- **为什么现在可默认**：符合低维护目标，具体差异仍会在功能任务中展示后再定。

### D7：基准素材采集节奏

- **推荐答案**：M0 只收集简洁模式验收所需材料；其他功能到排期前再询问 1–3 个会改变验收契约的
  使用习惯，自然事件样本随出现补充，不要求用户一次性整理全部旧版记忆。
- **影响**：减少前期负担，同时避免实现到一半才发现入口、使用顺序或反馈基准错误。
- **为什么现在可默认**：源码能还原结构但不能证明实际使用习惯；按需询问更准确、摩擦更低。
