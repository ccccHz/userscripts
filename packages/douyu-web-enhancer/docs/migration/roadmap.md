# Douyu Web Enhancer 完整迁移路线图

最后更新：2026-09-11

本路线图把“逐步迁移直至完整”解释为：先完整登记归档能力，再由用户确认保留范围，对保留项逐个
实现和实机验证；过期、危险或用户不需要的功能可以有证据地放弃，而不是为了数量强行实现。

斗鱼接口来源、`show_time`/`todayWatch` 边界、公开项目对比和后续研究 TODO 见
[DouyuEx 接口研究与对比](../research/douyuex-api-landscape.md)。该研究不改变已批准的迁移范围。

2026-09-04 已确认采用“全量登记、安全价值优先”，并先用简洁模式 M0 完整验收试跑和校准验收流程。
试跑结论见 [M0 验收工作流复盘](m0-acceptance-workflow.md)。

执行节奏遵循 [DouyuEx 任务分流规则](../task-routing.md)：先完成并确认体验契约，再以一次执行任务完成已锁定范围；核心返工视为前置盘点/验收缺口，而非正常迭代。

## 完整迁移的完成定义

五个维度必须分别统计，禁止用一个百分比混淆：

1. **归档功能全量登记**：归档的已注册、间接注册、未注册和明确失效能力都进入
   [归档索引](archive-inventory.md)。本项完成不代表承诺迁移。
2. **确认保留范围**：每项有 `keep / defer / reject` 用户决策或采用了已声明的安全默认值；未确认项
   不能进入 `planned`。
3. **已实现**：保留项具备唯一状态所有者、幂等启停、清理、诊断和自动化测试；只能标为
   `implementing` 或 `verifying`。
4. **已实机验证**：配置、runtime、页面结果、体验四层证据全部通过，才在 `features.json` 标 `done`。
5. **明确放弃**：记录原因（过期、已有官方替代、风险大于价值或用户不需要）和重新开启条件。

项目可称“完整迁移”当且仅当：全量登记无遗漏；每个登记项属于 `done`、`deferred` 或 `rejected`；
所有用户确认保留的项均为 `done`；没有用旧聊天、临时任务 ID 或隐含范围解释遗留项。

## 总体依赖顺序

```text
基准与范围确认
  → 完成简洁模式验证/入口壳稳定
  → 纯本地、低风险原子功能
  → 本地数据与只读登录信息
  → 单域网络与媒体工具
  → 经确认的账号请求
  → 经专项调研的 Hook / WebSocket / 跨平台 / 自动化
  → 逐项关闭 deferred/rejected，完成范围审计
```

源码模块、数据源或 package 归属不是体验/迁移单元。排阶段和优先级前，先按同一页面区域、同一操作
路径、共同显示或切换、相互遮挡及必须共同验收的关系，在 `archive-inventory.md` 登记体验簇/验收簇，
并为整簇写清组合验收契约。跨 package 但体验连续的能力也要建立关联，防止因实现归属不同而漏迁。

体验簇不改变工程边界：共享 UI、选择器或连接只是依赖，内部模块、状态所有者和失败隔离仍可独立；
跨 package 的实现仍分开建任务、版本和发布。原子功能可以分别实现，但只有原子证据与所属体验簇的
组合证据都通过，相关体验才算迁移完成。

## 阶段路线图

### M0：锁定基准与完成现有简洁模式

目标：把当前“实际体验良好”固化成可回归证据，不再出现设置、runtime、按钮都显示开启而页面没生效。

- 完成 `compact-player`、`chat-decoration-cleanup`、`chat-layout`、`room-metrics` 的普通/网页全屏/
  浏览器全屏、独立开关组合、刷新、换房、动态重建和停用恢复矩阵。
- 只采集本次简洁模式需要的 UI/操作记忆；缺失截图不阻止纯源码事实登记，但阻止相关 UI 等价结论。
- 稳定 `extension-entry-shell`，让未来功能都能复用可发现的近场入口和反馈，不退回 GM 菜单堆积。
- `danmaku-availability` 已完成窄范围实现与自动化回归；普通页没有特殊时期 `0` 样本，状态保持 verifying/长期自然验证，不把构建证据写成真实恢复通过。
- 把本次验收作为工作流试跑：逐项记录准备/执行耗时、重复步骤、失败点、可自动化项，以及配置、
  runtime、页面结果、体验证据中哪些可安全合并采集。
- 在 `docs/verification.md` 的 M0 记录下增加工作流复盘，明确保留、删减或自动化的步骤，再更新后续
  功能基准卡片和验证模板。可以合并采集动作，但四层结论仍分别记录，不能重新制造单层假阳性。

退出条件：四层证据齐全；现有简洁模式没有未解释的状态失配；`features.json` 只反映已验证状态；
工作流复盘已记录耗时、重复、失败、自动化和证据合并结论，并形成下一批可复用的调整版流程。

### M0.5：进入直播间的播放器定位与网页全屏恢复

- 用户问题是两个相连的斗鱼原生体验缺口：部分直播间顶部推广遮住播放器，用户须手动寻找画面；网页全屏状态不持久化。`auto-web-fullscreen` 把“定位 → 按全局状态决定网页全屏”作为一次原子到达事务，`compact-player` 仍只拥有独立礼物栏布局设置。
- 数字直播间到达事务依次等待真实播放器可操作、执行一次定位、读取全局网页全屏偏好；true 时对**可语义确认**的官方网页全屏控件尝试一次，false 时结束。成功、控件明确不可用/验证失败或用户主动接管都是终点；刷新或真实 SPA 换房才可开始下一次事务。
- 启动时序所需的有界等待或验证只能发生在该事务结束前，不能演变为同页位置维护。控件没有完成“唯一选择器 + 进入标记/几何验证 + 退出恢复”的闭环时，停在安全降级，不使用图标顺序、哈希全名、持续 observer 或轮询作为替代。

## 每日自动化体验与共享运行时

`daily-sign-in` 不再预设为“先实现手动 `sign-room`”。在产品层，它属于更大的“每日自动化”体验组合：

- 归档 `douyu-web-enhancer` 的多个 `sign-*` 子任务；
- 归档 `fans-badge-renewal` 的低自动化一键续牌；
- 现有独立 package `packages/auto-fans-continue` 的自动送荧光棒能力。

2026-09-13 用户确认把现有 `packages/auto-fans-continue` 整套并入本包，并以其当前实现、默认行为、
配置、锁、日志、toast 和测试为唯一荧光棒迁移基准，不采用归档 `DailyAuto` 或
`fans-badge-renewal` 的实现。合并完成前，原 package 继续作为可运行基准，不能提前删除。

每日自动化建立共享运行时，但不使用一个粗粒度全局锁或一个“今日完成”状态包办全部任务：

- 页面级启动认领防止同一 document 重复入口；跨 tab 使用带 owner、开始时间和过期时间的任务锁；
- 每个任务独立保存最后尝试、最后确认成功、结果摘要和重试资格；仅经响应或任务前后状态验证后完成；
- 同一任务重复触发应幂等，陈旧锁可安全接管，某一任务失败不得阻塞其他任务；
- toast 只提供用户可读汇总，有界持久审计日志记录原子动作和验证证据，并可从统一配置页复制；
- 日志不得保存 Cookie、token、完整授权 URL 或不必要的账号隐私。

第一批范围为鱼吧签到（不含补签）、客户端签到、粉丝家园、超级粉丝、固定读帖、固定关注任务、
等级奖励领取和现有自动荧光棒。`sign-room` 最后做单房受控实测；活动型签到进入延伸验证 TODO。
任何账号请求、关注变更、送礼或自动执行仍要在具体实机操作前逐项说明并确认权限。

统一配置页是该体验的近期前置任务：集中管理全包功能开关、默认值、自动化参数、执行状态和日志入口。
原页面的高频就近入口继续保留；GM 菜单只在配置页完成前承载自动荧光棒目标房间等临时配置。

### M1：低风险播放控制（迁移批次 1）

按独立任务依次迁移：`volume-wheel` → `video-sync` → `video-recall` → `video-speed` →
`highest-quality` → `disable-offline-jump`。它们价值高、账号风险低、可用单页明确验收。

组合策略：统一放入播放器近场体验，但每项拥有独立设置和 runtime。`disable-offline-jump` 必须先移除
归档永久轮询方案；`highest-quality` 必须尊重用户手动选择。

### M2：低风险弹幕编辑与阅读（迁移批次 2）

`message-context-reply` → `danmaku-tail` → `chat-memory` + `danmaku-send-check` → `shield-entry-messages` →
`shield-danmaku-background`。`chat-length-extension` 先实测当前限制后再决定是否插入本批。

组合策略：`chat-memory` 与 `danmaku-send-check` 属于同一 `chat-sending-experience`
验收簇，但分别拥有持久历史与瞬时发送队列，任一失败不阻断另一项。入口可以共享输入区/右键卡片宿主，但发送前修改、纯填充和纯 CSS 屏蔽绝不共用状态。
真实验收必须检查实际输入/发送/显示结果，而不是只检查监听器、属性或节点存在。

### M3：本地数据与只读信息（迁移批次 3）

`last-live-time` → `bag-info`（只读，不含清空）→ `barrage-speed` → `danmaku-collection`。
`follow-list` 在用户接受登录态只读请求后加入；`room-vip-expiry`、`fans-badge-date` 只有当前页面仍存在时加入。

组合策略：信息卡片可共享视觉规范，不共享缓存。任何只读功能都不得顺手带入相邻的送礼、删除或关注动作。

### M4：播放器增强（迁移批次 4）

`prevent-auto-pause` → `video-zoom` → 普通 `video-filter` → `cinema-mode`。先比较官方能力；已有官方等价
功能时优先登记放弃或只保留差异价值。全景滤镜、相机 GIF 不随普通滤镜迁入。

组合策略：共同维护 transform/filter 组合顺序和恢复契约；仍按原子功能独立任务。里程碑结束后统一跑
普通/两类全屏和画质切换回归。

### M5：单域网络与媒体工具（迁移批次 5）

`copy-live-stream` → `audio-only-line` → `streamer-metadata`；视频页另建 `video-danmaku-heatmap`、
`video-download`、`video-danmaku-export` 任务。每增加一个 `@connect` / `@grant` 必须重新请求用户确认。

组合策略：真实流解析可以成为小型共享服务，但调用者各自处理加载、失败、过期和清理。下载与导出因
文件体积、第三方库和隐私边界不同，不能合并。

### M6：明确选择后的高风险能力（迁移批次 6）

按用户选择分成互不阻塞的研究轨：

- **每日自动化实现轨**：先完成共享调度、按任务锁、运行账本、审计日志和统一配置页，再迁移已确认的
  原子任务；自动荧光棒只搬运现有实现。`sign-room` 已于 2026-09-19 单房实测确认接口下线并放弃。
- **账号请求轨**：只执行每日自动化评估确认保留的原子请求；送礼、禁言、关注变更仍需逐项授权。
- **消息协议轨**：`shield-repeated-danmaku` 及其他确实需要完整消息流的能力；
  `danmaku-send-check` 已在用户授权后加入匿名只读 WS，以公共流、本人 DOM 行和 2 秒窗口恢复
  `suspected` 提示；登录态 WS、UID/Cookie/Token 和发送能力仍不在授权范围内。
- **复杂媒体轨**：`enhanced-pip`、`popup-multiview`、跨平台流；每个平台分别授权和验收。
- **全局 Hook 轨**：`danmaku-availability`、`block-p2p-upload`、`tab-keepalive`、`restore-closed-yuba`；
  先证明当前机制，再做最窄、可撤销 Hook。
- **自然样本优化轨**：SC 工具栏遮挡继续依照 [专项调研](../research/sc-toolbar-obstruction.md)，不混入
  DouyuEx 等价迁移。

退出条件：每个高风险能力都有明确用户授权、风险边界、失败行为和真实页面证据；未获确认项转
`deferred` 或 `rejected`，不悬空。

## 现有 `danmaku-availability`、`daily-sign-in` 之外的合理 3–6 批

推荐顺序就是 M1–M6。前四批优先兑现高频、低账号风险、独立可验收的价值；第五批才扩大网络/
文件权限；第六批把账号写入、反检测、过期活动、复杂 WebSocket 和跨平台能力隔离。这样即使特殊
时期样本或每日自动化评估/授权迟迟不到，也不会阻塞其他安全功能；二者不是 M1 的前置实现。

## 每个功能的轻量迁移流程

### 1. 迁移前基准卡片（先写，控制在一页内）

- 稳定 ID、用户价值、所属体验簇/验收簇、簇级优先级和明确不在范围内的相邻能力。发现共同显示、
  共同切换、相互遮挡或操作路径连续的功能时，先补齐整簇盘点和组合验收契约，再排原子实现。
- 归档源码入口、页面/UI/长按等触发入口、文案、默认值、持久化键与恢复时机。
- 输入/输出、页面影响区和必须保留区；普通/全屏/动态重建状态矩阵。
- 外部域名、账号动作、权限、隐私、失败行为和用户确认记录。
- 证据标签：归档事实 / 源码推断 / 用户确认 / 当前页面实测。

基准不完整时状态保持 `inventory` 或 `research`。不要为了开工先造新 UI。

### 源码为什么不能说明“实际怎么用”

源码可以确认入口结构、事件绑定、默认值、持久化键和理论反馈，但不能确认用户真实习惯和当前价值：

- 用户是否发现过、是否实际使用这个入口；
- 功能是常开、每天一次，还是只在特殊场景临时开启；
- 真实操作顺序，是否依赖长按、先打开某面板或先切换页面模式；
- 用户用什么视觉/文字反馈判断成功，哪些反馈是不可缺少的；
- 斗鱼当前官方近似能力是否已经足够，旧增强的差异是否仍有价值；
- SC、特殊时期限制、收藏满、下播跳转等罕见自然场景的真实表现；
- 常用设备、浏览器、缩放、普通/网页全屏/浏览器全屏和未登录等页面模式。

这些属于**用户习惯或当前页面事实**，不能从代码臆测。也不要求用户一次性整理：每个功能进入排期前，
先用源码填满能确定的基准，再只询问 1–3 个源码无法回答且答案会改变范围、入口或验收契约的问题；
不影响契约的偏好延后，罕见自然样本随出现采集。

### 2. 选择最窄实现

1. 归档实现仍适合当前页面时，直接提取成熟的纯函数/CSS/交互片段并保留来源记录。
2. 只有选择器、宿主或页面模式变化时，做最窄兼容；选择器集中进入 registry。
3. 只有原实现不可撤销、全局污染或已被站点结构阻断时才重写，并记录偏差。
4. 不整包迁入 `require/`；不因“将来可能复用”增加状态层、observer、定时器或 DOM 标记。

### 3. 唯一状态所有者

- 持久开关：schema 化 GM 设置是唯一规范状态。
- 瞬时动作：feature runtime 的当前操作状态是唯一所有者，不伪装成持久设置。
- 房间实时数据：只属于当前房间内存状态，换房作废。
- 按钮、CSS、DOM 属性、诊断都是派生结果；不能互相回写形成第二状态源。

### 4. 四层证据，逐层推进

| 层 | 最少证据 | 常见假阳性防线 |
| --- | --- | --- |
| 配置 | 默认、保存、刷新/换房读取 | 设置正确不等于页面生效。 |
| runtime | 启用、重复启用、停用、清理、错误状态 | runtime `active` 不等于 CSS 命中。 |
| 页面结果 | computed style、几何、真实输入/媒体/请求结果；相邻保留区 | 节点/style 存在不等于用户看见或点得到。 |
| 体验 | 入口位置、文案、步骤、反馈、全屏/重建/恢复与归档对照 | 按钮亮起不等于实际功能开启。 |

### 5. 验证节奏

- 单功能开发：先跑相关测试文件、类型检查和 package 构建。
- 体验组合里程碑：再跑 package 全测与 `pnpm validate && pnpm test && pnpm type-check && pnpm build`。
- 真实斗鱼页面只做最后验收，不拿在线页面替代可重复单测；账号写入只在单独授权后执行。
- 实机记录写入 `docs/verification.md`，包含 URL 类型、页面模式、操作路径、反馈、结果、恢复和诊断；
  不记录 Cookie、账号数据或聊天正文。

## 防止已知回归的设计门槛

- **UI 开启但未生效**：测试必须从设置一路驱动 runtime，并断言计算样式/几何/真实结果；禁止把
  `aria-pressed`、根属性、style 节点或诊断 `active` 当成最终断言。
- **入口遗漏**：基准卡片必须同时列原入口、备用入口、文案、可发现时机和反馈；高频功能不能只放 GM 菜单。
- **全屏/动态重建遗漏**：每项声明恢复触发器。静态 CSS 自动覆盖后挂载节点；observer 只重新挂载
  入口或同步 CSS 无法表达的模式。普通/网页全屏/浏览器全屏至少各验一次。
- **observer 自激**：共享 observer、局部查询、合并调度；写 DOM 前比较旧值；测试连续 mutation 后
  调度次数有上界，停用后无订阅和节点残留。
- **只验证 DOM 存在**：每个验收写成用户结果，例如“按钮中心命中自身且排行榜计算高度为 0，弹幕区
  高度增加，统计摘要仍可见”，而不是“按钮/类名存在”。

## 调度中心的低摩擦任务模板

后续每个执行任务只需传递以下稳定信息：

```markdown
目标：迁移/调研 `<feature-id>`，交付一个可独立验收的结果。
作用域：实现仅限所属 package；列出所属体验簇及跨 package 关联，明确本任务不实现的簇成员和相邻账号动作。
必读：
- `userscripts/AGENTS.md`
- `userscripts/packages/douyu-web-enhancer/AGENTS.md`
- `docs/migration/archive-inventory.md` 中 `<feature-id>` 行
- `docs/migration/roadmap.md` 的轻量迁移流程和所属阶段
- `docs/migration/features.json` 中对应契约（若已登记）
- 归档源码入口与当前实现/测试入口（只读最小集合）
验收信息：归档入口/文案/默认/持久化；状态所有者；影响区/保留区；恢复触发器；
普通/全屏/重建矩阵；原子与簇级四层证据；外部域名/账号动作/失败行为；批准的偏差。
验证：相关定向测试 + type-check + package build；里程碑才跑全量门禁；最后实机。
权限：发布、推送、安装、metadata 权限、账号操作、数据删除均需当次确认。
回写：稳定契约写 `features.json`，实机证据写 `verification.md`，不附旧聊天或 task/thread id。
```

最少读取集故意不要求重读全部归档。只有 inventory 指向多个文件、功能依赖共享协议或基准缺失时才
扩读；这能降低 token 和上下文摩擦，也让任务从文档独立恢复。

## `features.json` 更新策略

不把全量 inventory 写入 `features.json`，因为源码存在不等于用户确认保留。D1 已确认的是筛选原则，
不是全体功能的保留决定。用户逐项确认某项后：

1. 新增原子 feature 条目及所属 experience profile；状态从 `inventory` 起。
2. 写完整 contract、外部权限、状态所有者、恢复触发器和偏差门槛。
3. 只有四层证据齐全才改 `done`；明确不保留的项在 inventory/user-decisions 留下理由即可，避免让
   发布清单膨胀成旧项目墓地。
