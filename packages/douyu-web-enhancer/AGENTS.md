# Douyu Web Enhancer working agreement

本文件适用于 `packages/douyu-web-enhancer/`。同时遵守仓库根 `AGENTS.md`；冲突时以这里更具体的
迁移契约为准。先读 `docs/README.md` 和 `docs/migration/features.json`。

## 迁移基准

- 归档版本的代码、实际运行表现和用户提供的原版截图共同构成 UI、交互和状态处理的验收基准，
  不是可自由取舍的设计参考。
- 开始实现前必须完成对应功能的基准清单，至少确认核心行为、入口位置、文案、默认值、启停反馈、
  持久化语义、恢复时机、影响区域和必须保留的相邻区域；基准不完整时保持 `inventory` 或
  `research`，不得进入重写。
- 斗鱼 Web 没有发生使原实现不可行的结构或行为变化时，必须等价迁移，不主动改变入口、控件
  形式、文案、反馈、布局、默认值、持久化和状态语义。
- 内部架构可以重写和解耦，但不得以工程化、复用或实现便利为理由改变已验证的用户体验。
- GM 菜单只用于诊断、低频全局设置或页面 UI 不可用时的兜底；不能替代原页面内的高频入口。

## 迁移 one-shot 就绪门槛

- 这是已有功能迁移，不是从零产品探索。派发实现前，必须先围绕真实体验消除会改变范围的歧义，并取得用户对短而完整契约的确认；契约至少包含用户问题、原版行为/入口/默认值、操作顺序、持久化、触发/终止/接管、失败/降级、保留区域、非目标、真实样本和验收路径。调度细则见仓库 [任务分流规则](../../docs/task-routing.md)。
- 归档源码、当前页面和已有文档可确定的事实先自行盘点，只询问真正改变体验或范围的缺口；未锁定前保持沟通/盘点，不进入实现。确认后冻结体验范围，默认以一次执行任务完成代码、自动化、文档同步和可安全完成的真实 E2E。
- 契约冻结前按“整理体验事实 → 以 1–3 个问题澄清 → 更新完整契约 → 再审查”循环，直到没有实质歧义；无法消除但不阻塞的假设与回退必须记录。实现不得把网页研究、DOM 观察、源码检查或单元测试当作 E2E：核心路径必须运行修改后的实际构建产物，并记录“前置状态 → 用户操作 → 最终结果”和重要负面结果；未执行即为未验证。
- 实现中遇到契约外选择或体验证据不足必须回到澄清；选择器、DOM 适配和工程组织可自主处理，但不得改变体验。需要安装、账号权限或罕见自然事件才能取得的证据可使状态保持 `verifying`，但不能遮蔽普通核心路径未覆盖。
- 对已确认契约的真实浏览器验收，可执行刷新、滚动、网页全屏进/退、普通显示开关和状态读取等可逆非账号操作；不得借此点击/领取活动或广告、改画质或扩大范围。消息、签到、送礼、充值、关注、订阅、登录、账号设置、删除数据及其他账号/付费/对外操作仍逐项请求确认；非契约核心的浏览器原生全屏不自动执行。
- 实现后发现核心体验返工时，必须将其记为前置盘点/契约/验收缺口并反哺本规则或验收材料；不得把反复补丁视为正常迁移节奏。同一冻结契约的直接修复继续原任务，独立功能和不同 package 仍按仓库分流规则拆分。

## 偏差门槛

省略或改变旧 UI/交互前必须暂停实现，在 `docs/migration/features.json` 对应契约的
`deviations` 中记录基准、方案、理由、可验证目标和回退方案。取得用户明确确认并写入
`decisionRecord` 后才能实施；未获确认的差异属于迁移缺口。

## 实现约束

- 用户明确的问题与体验目标是设计、实现和验收的最高层边界；源码模块、归档实现、选择器适配和技术容错都不得自行扩大体验范围。先用用户真实操作路径说明“解决什么缺口、完成后什么不应再发生”，再选择实现。
- 顺序耦合的一次性体验必须登记为一个原子体验事务：写清触发、步骤顺序、状态输入、成功/明确降级终点、用户接管点，以及下一次允许重启的生命周期事件。内部可拆模块和状态所有者，但不得拆成会独立重入、持续纠正或互相争夺页面控制的 runtime 动作。
- observer、retry 和 timer 只能帮助尚未结束的事务到达本次终点；事务成功、明确降级或用户接管后必须全部停止，且同一生命周期不得重启。只有刷新、真实 SPA 换房或契约明确的新触发可建立下一次事务。
- 每个原子功能必须有稳定 ID、默认状态、启用/停用清理逻辑和诊断状态。
- 每个功能必须声明唯一的规范状态所有者（single source of truth）。持久化设置、runtime、按钮、
  CSS 和 DOM 标记不得各自形成独立状态；其余层只能由规范状态派生并可重复恢复。
- 新实现相对归档版本每增加一个状态层、永久 observer、定时器或 DOM 中间标记，都必须在迁移
  契约中写明它解决的具体页面行为和验证方法；没有可验证必要性时不得引入。
- 验收以用户真实操作路径表述，并记录负面结果：完成后不得再抢滚动或焦点、重复点击或扩展到广告处理、浏览器全屏等相邻能力。
- DOM 适配集中在选择器注册表；优先使用状态属性和集中 CSS，不覆盖网站完整内联样式。
- CSS 本身能覆盖当前及后来挂载节点时，不得使用 observer 重复写样式或属性。Observer 只负责
  CSS 无法表达的节点挂载、动态测量或页面模式同步。
- 页面观察使用共享 `MutationObserver`；除明确的短期重试外，不增加永久轮询。
- Observer 订阅者的 DOM 写入必须幂等；全页观察合并调度并限制扫描频率，不能被自身写入持续唤醒。
- 新功能默认保持 `userscript.publish=false`。修改产物时仍按根规则提高 package 版本。

## UI 等价与状态矩阵

“功能已迁移”同时要求核心行为、入口位置、操作步骤、状态反馈、默认值和持久化方式满足契约。
源码模块、数据源和 package 边界都不自动等于用户体验或迁移单元。同一页面区域、同一操作路径、共同
显示、共同切换、相互遮挡或必须共同验收的功能，开始实现前必须先登记为一个“体验簇/验收簇”，
一起完成盘点、优先级和组合验收契约。体验簇可以跨 package；跨 package 的连续体验必须在路线图中
互相引用，不能因代码归属不同而漏迁或拆散验收。

体验簇只约束产品盘点和验收边界，不要求把同区域代码合并到同一 package 或 runtime。内部仍应保持
合理的独立模块、唯一状态所有者、失败隔离、版本和发布生命周期；实现任务也继续按所属 package 分流。
例如简洁模式中的聊天区布局与 `room-metrics` 统计摘要来源和状态独立，但二者共同显示、可能相互遮挡，
所以必须成簇检查“弹幕区拉高后统计摘要仍可见”，不能只分别证明两个模块已运行。

简洁模式至少覆盖：

- 普通页面；
- 网页全屏；
- 浏览器全屏；
- 礼物栏、弹幕前缀、排行榜三个独立开关的全部相关组合；
- 启用、停用、刷新和切换房间后的状态恢复；
- 目标区域生效且相邻保留区域未被误伤。

## 完成门槛

- 运行 `pnpm validate && pnpm test && pnpm type-check && pnpm build`。
- 验收必须分别覆盖配置读取、runtime 启停和清理、页面计算样式或几何结果、用户可见入口与反馈。
  设置值正确、runtime 已启用、CSS/节点存在或自动化测试通过，任何一项都不能单独证明功能完成。
- 真实页面验收逐项对照归档基准，并记录 URL、页面模式、入口、路径、反馈、恢复结果和诊断快照。
- DOM 节点存在、自动化测试通过或开关可切换，均不能单独证明 UI 迁移完成。
- 只有完整迁移契约通过真实验证后，才能把清单状态更新为 `done`。
