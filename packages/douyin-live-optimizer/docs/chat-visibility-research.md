## 方案选择前必须验证

1. 响应有没有“成功但被过滤”的可重复标志；字段位于 HTTP 响应、原始推送还是网页加工后的消息，分别记录。对照原始消息 ID，排除 `is_mock`。
2. 原始推送的审核/可见性字段能否对应真正的接收端差异；字段缺失或 false 不能直接判公开可见。
3. 若依赖独立接收：必须证明观察者身份与发送者隔离。同账号新标签、复制已登录 socket URL，不能当匿名观众证据。还需核实签名时效、游客身份、连接健康、重连与消息丢失。
4. 公开代码目前可借鉴采集流程，没有找到可直接拿来当当前抖音有效判定规则、附带正反样本的屏蔽检测实现。

## 屏蔽词与测试样本准备

未找到带当前房间、时间、独立接收端记录的可靠“通用必屏蔽词”样本。网上词表混有商品宣传违规词、视频审核词、主播自设词和过期资料，不能据此宣称某词当前必定导致直播弹幕暗屏蔽，也不能拿“没收到”倒推词有效。

优先阳性来源：用户可控测试房间内明确设置的无害自定义词（例如临时测试标记），或者用户已有且愿意复验的实际暗屏蔽案例。与普通聊天对照，样本正文、房间与发送操作在执行前确认。若没有可控房间，先只采集用户自愿发送的正常消息与自然发生异常；此阶段不能保证获得阳性。

| 场景 | 采集与操作 | 验收要求 |
| --- | --- | --- |
| 普通文字阴性 | 发送者正常手动发一条；独立接收端对照 | 同一消息 ID/可靠身份及内容匹配，确认健康链路和本地回显差别 |
| 可控房间过滤阳性 | 管理端已确认的自定义词、未命中对照词各一条 | 返回受理/自己回显，独立接收端差异，排除账户禁言和本地屏蔽 |
| 既有真实异常 | 用户确认愿意复验的样本 | 不预设字段值；同时记录 HTTP、原始推送、本地回显和独立端 |
| 审核延迟 | 正常持续观察，短窗/10秒/30秒分段核对 | 迟到能纠正；不把首个超时写成确定屏蔽 |
| 重复内容/其他人同文 | 不同 ID、发送者、时间的对照样本 | 不能仅按正文把他人消息当自己的公开确认 |
| 断线/后台/换房 | 接收端重连、后台挂起、SPA 换房 | 异常窗口标不可判断，旧房结果不污染新房 |
| 表情/富文本/多行 | 后续单独覆盖 | 未支持的类型明确不判断，不套普通文本规则 |

分阶段执行：先用用户手发的 2–3 条正常消息核对采样接线；接线正确后，再按 B 站既有测试方法收集约 20 条互不重复正常样本、分不同房间/时段观察尾延迟。屏蔽候选每条一次、独立分类，不混入延迟统计；既有 B 站词条也不能直接视作抖音阳性。

先做正常消息基线，才确定正式观察窗口。输出状态预计分“公开接收已确认／未观察到，疑似／观察不可用／平台明确拒绝／待审核线索”，不输出“所有人必定可见”。

本地证据只保留测试所需字段与样本编号；不提交 Cookie、签名 URL、Token 或完整身份/原始响应。真实发送由用户选择内容操作；不自动刷词或重发。
