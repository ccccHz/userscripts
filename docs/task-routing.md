# 开发任务编排与分流规则

这份文档是 userscripts 多包仓库的长期任务分流依据。任务归属由 package、验收契约和当前改动
决定，不依赖聊天历史、临时 task id 或 thread id。

## 调度中心定位与任务形态

当前保存项目的主对话是“调度中心”，负责需求澄清、体验事实确认、范围冻结、任务创建与跟踪、
结果汇总和最终独立验收；原则上不直接承担一个完整迁移功能的实现。

任务按预计交付形态分为三类：

1. **独立可见任务对话**：预计跨多个阶段、会修改功能代码、需要真实浏览器验收、可能等待用户反馈，
   或需要单独统计模型/额度的工作。每个完整、可独立验收的迁移功能必须使用此形态；由调度中心显式
   创建侧栏可见的 Codex 任务对话，不能只作为内部 subagent。创建时必须显式传入模型和推理等级，
   并保存返回的 task/thread ID。
2. **内部 subagent**：只读、边界明确、可并行、一次性返回可压缩短结果的工作，例如源码检索、API 调研、
   独立代码审查或测试矩阵检查。一个内聚功能不得为并行而机械拆成多个 subagent。
3. **调度中心直接完成**：几分钟内可完成、不修改 `packages/` 功能实现、不会污染主要上下文的检查、
   状态核对或长期规则维护。

同一交付物的补查、直接修正或复验可以复用原 subagent；新功能、不同交付物或上下文已经混杂时必须
新建任务/agent。优先复用角色模板和冻结契约，不无限复用旧上下文。

## 当前阶段的派发任务模型策略

用户于 2026-09-11 明确决定：调度中心保持其当前模型与推理配置，本规则不改变它；所有由调度中心
派发、继续或委派的任务 chat 一律使用 `gpt-5.6-terra` 与 `high` 推理，作为当前测试配置。

该测试策略替换 2026-09-05 的“所有任务 Sol medium”规则。不得继续向派发任务指定
`gpt-5.6-sol`、`medium`，也不得按任务表面上的代码量或文档属性自行改用其他模型或推理强度。
只有用户以后再次明确调整时才能改变；性能、成本或调度器默认值不能自行覆盖它。

### 每轮不可跳过的调度检查

1. 主对话先确认自己是调度中心，并读取本文件；上下文摘要或先前已经读过都不能替代本轮检查。
2. 将请求分类为澄清/盘点、独立功能执行、短只读 subagent、调度中心短检查、验收或汇总。预计跨阶段、
   修改功能代码、需要浏览器验收/用户反馈或单独统计额度的工作，必须创建独立可见任务对话。
3. 完整功能派发前必须已有用户确认的书面冻结契约。创建/继续独立任务时显式写入
   `gpt-5.6-terra` 与 `high`；不得依赖默认配置。没有成功返回的 task/thread ID，不得在主对话代做实现。
4. 创建独立任务前后更新 `docs/task-execution-metrics.md`；主对话只做必要的只读协调、独立验收和最终归档。
5. subagent 只可承担本页允许的短任务；不得用内部 subagent 代替一个完整功能的独立可见任务。

用户只说“继续”时，含义是继续上述调度流程或继续已解析的执行任务，不是取消分流规则。若执行任务
因额度、系统错误或用户叫停而结束，记录为中止样本，不以主对话补做来掩盖。

## 模型与消耗实验记录

当前 Codex 可读取的是账户 5 小时/每周窗口的总体已用百分比和任务持续时间，不提供可靠的逐任务、
逐阶段精确 token 明细。因此实验同时记录：模型、推理强度、任务类型、开始/结束时间、墙钟时长、
窗口使用率前后值、执行/验收/文档的轮次与命令次数、返工次数和结果。窗口百分比是粗粒度估算，若
期间有其他任务运行必须标记为受污染；不得把它写成精确 token。

要比较模型时使用相近规模的后续真实任务，提前采集基线并各自独立完成；不为制造对照而重复已经完成
的账号动作或代码实现。中途换模型、事后补派复核、未采集起点或被额度中止的任务均单独标为无效/辅助
样本，不纳入“每项功能需要多少额度”的主比较。

## 分流决策

1. 先从目标页面、源码入口、测试或现有文档识别所属 `packages/<name>`。
2. 需求属于不同 package 时，实现必须分开建任务；不要把多个 package 的代码改动塞进同一执行任务。
   但 package 边界不等于体验边界：跨 package 且同一操作路径、共同显示/切换、相互遮挡或必须共同
   验收的能力，应先在路线图中关联为体验簇，并建立簇级盘点、优先级和验收任务。
3. 同一 package 且属于同一验收契约、当前未完成改动的回归或其直接修复时，继续原任务。
4. 同一 package 的独立新功能，只要可以单独设计和验收，就新建任务。
5. 同时影响多个 package 的共享代码、构建、验证、发布或仓库结构，建立仓库级独立任务。
6. 无法可靠识别 package 时，先建立只读盘点任务；确认入口和边界后再分流实现。

## 体验事实确认与契约冻结

调度者先依据归档源码、原版截图/实际表现、当前页面和已有文档整理体验事实与初版契约，并显式列出所有仍可能改变行为、范围、状态、触发/终止、用户接管、失败方式或验收结果的模糊点和假设。

按“整理 → 提问 → 更新 → 再审查”反复推进：每轮只向用户提出 1–3 个真正影响契约的问题；收到回答后更新完整契约、重新审查剩余歧义。不得因为已沟通一轮或任务看似简单而提前实现。归档、页面和文档已可确定的事实必须先自行盘点，不能转嫁为用户问题。

直到尽可能消除全部实质性模糊区域，才向用户复述一份短而完整的冻结契约并取得明确确认。无法彻底消除但不阻塞的假设必须显式记录及其回退；会改变体验的歧义必须停止，不得自行选择。未确认或仍有实质歧义时不得派发实现。

## 迁移 one-shot 就绪门槛

已有功能迁移的默认质量目标是：契约确认后由一次执行任务完成实现、自动化、文档同步和当时可安全完成的真实 E2E，而不是把基本体验边界留给后续补丁。沟通/盘点任务可以多轮持续；未达到本节门槛前不得派发实现任务。

调度前必须形成短而完整、经用户确认的体验契约，至少包含：

- 要解决的原始用户体验，以及可见的成功结果。
- 原版行为、入口、默认值和已知实现；当前实现、已有缺口与可复用基础。
- 本次必须实现的范围、明确不实现的范围、保留区域及相邻体验簇边界。
- 状态所有者、持久化、跨页面/跨房间边界、触发、终止、用户接管和失败/降级行为。
- 可由真实浏览器重复执行的验收步骤：目标 URL、前置状态、用户操作、刷新/持久化、页面模式变化、
  手动接管后的负面结果，以及需要额外授权的账号动作。
- 相关源码、归档证据、文档、测试入口和验证命令。

能从归档源码、现有页面和现有文档确定的内容，调度者必须先自行盘点；只向用户询问会改变体验或范围的真实模糊点。允许多轮澄清，但在向用户复述并获确认前不得冻结范围或派发实现。

确认后的独立执行任务应按该冻结契约一次完成代码、测试、文档和可安全执行的真实浏览器验收。实施中
出现契约外选择、证据不足或会改变体验的歧义，必须停止并返回调度中心澄清；DOM 适配、测试组织和
工程细节可以自主解决，但不得借此改变体验。需要用户安装、账号权限、罕见自然事件或其他当场无法取得
证据时，可以保留 `verifying`，但这些例外不能掩盖普通核心路径尚未覆盖。

派发使用“最小充分上下文”：只传冻结契约、必要文件路径、已知证据、权限边界和验收命令，不复制调度
中心全部历史。独立任务以仓库内契约、代码和文档为事实来源；聊天口头约定若会影响实现，必须先写入契约。

实现后仍发现核心体验边界并需要返工时，记录为前置盘点、契约或验收设计缺口，并回写长期规则/验收材料；不得把连续补丁常态化。同一冻结契约的直接修复仍继续原任务；不同 package 或独立新功能仍按本页分流规则拆分。

## 真实浏览器产物验收

Computer Use/真实浏览器验收必须运行修改后的实际构建产物。实现前的网页研究、DOM 观察、手动模拟、源码检查和单元测试都不能替代产物 E2E。每条核心路径记录“前置状态 → 用户操作 → 最终可见/几何/持久化结果”，并包含重要负面结果；未实际执行的项目必须明确标为未验证，不得推断通过或按完成汇报。

普通核心路径应在同一次执行任务内完成产物 E2E；若用户安装、账号权限、罕见自然事件或其他外部条件使其无法验证，任务保持 `verifying` 并说明阻塞原因。这些例外不能掩盖普通核心路径未覆盖。

调度中心必须在执行任务返回后进行独立验收，不能仅采信任务自述。UI 和体验功能至少覆盖修改后实际
产物的刷新、持久化、相关页面状态变化、用户手动操作后的行为和冻结契约中的重要负面结果。执行任务的
浏览器记录可以作为证据，但不能替代调度中心对关键路径的独立复核。

## 默认可逆 UI 验收授权

为验收已确认契约，调度者可在用户当前指定或相关浏览器页面执行可逆、非账号性的操作：刷新、滚动、网页全屏进/退、展开/关闭普通显示开关，以及读取页面状态；无需为这些契约内步骤重复询问。该授权不扩大产品范围，也不允许点击或领取广告/活动、改变播放质量等无关行为。

发送弹幕或消息、签到、送礼、充值、关注、订阅、登录、修改账号设置、删除数据及其他账号、付费或对外操作，仍须逐项获得明确授权。浏览器原生全屏或其他可能干扰用户环境的操作，若非契约核心也不自动执行。

## 调度任务边界

调度中心只负责澄清、识别归属、冻结契约、创建/查找可继续任务、跟踪、结果汇总和独立验收，不承载
完整功能实现。创建或继续执行任务前只读取仓库索引、目标 package 的局部规则、相关契约和直接文件入口，
并确认已满足“迁移 one-shot 就绪门槛”。

发布、推送、安装脚本、扩大权限、真实账号操作和删除数据始终需要用户单独确认；历史任务中的
授权不能自动沿用。

## 最小任务说明

执行任务只传递以下内容：

- **目标**：一个可以独立交付的结果。
- **作用域**：所属 package 或仓库级基础设施，以及明确不在范围内的内容。
- **体验关联**：所属体验簇、同区域/同路径成员和跨 package 关联；说明本任务负责的原子结果与簇级
  回归边界，不以体验连续为理由合并 package、状态所有者或发布生命周期。
- **约束**：根 `AGENTS.md`、package 局部 `AGENTS.md` 和相关契约中的必要条款。
- **验收条件**：可观察行为、回归边界及完成定义。
- **文件入口**：优先读取的源码、测试和文档路径。
- **验证命令**：覆盖本次改动的最小命令；仓库级交付再运行全量门禁。
- **权限门槛**：本任务是否触及必须再次向用户确认的操作。
- **执行配置**：调度中心保持当前配置；派发任务 chat 固定为 `gpt-5.6-terra`、`high`，只有用户明确
  调整后才可改变。

任务完成报告必须明确实际使用的模型与推理等级，并记录开始/结束时间、实现轮次、核心体验返工与普通
修复次数、自动化测试耗时、真实浏览器验收耗时、已知未覆盖项，以及可获得的额度窗口变化。无法获取
精确 token 时只能标记为总体窗口估算；并发或其他任务污染必须注明，不能将百分比差值伪装成精确消耗。

不要附带无关聊天记录、大段仓库背景、已完成历史或临时任务标识。执行任务完成后，把稳定结论、
契约变化和验证证据写回所属 package 或仓库文档。
